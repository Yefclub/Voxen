# Design System: Voxen

## Overview

**Creative North Star: "Documentary contact sheet"**

Voxen is a continuous knowledge workspace: ink and warm white, restrained emerald interactions, real content, and crisp thin rules. Documentary contact-sheet discipline gives records a clear title, quiet metadata, and room to be read. The Voxen name and transparent emerald folded-form symbol anchor the identity; Light and Dark express the same system.

The interface is precise and restrained. Flat surfaces and tonal layers organize work; softly shadowed overlays carry temporary context. Bricolage Grotesque supplies the display voice, Inter handles the interface and reading, and JetBrains Mono marks code and data. Mobile keeps the same hierarchy while moving contextual work into sheets.

**Key Characteristics:**

- One Voxen identity in Light and Dark.
- Documentary rows, aligned headings, and thin separators.
- Restrained emerald interaction with distinct status and knowledge colors.
- Self-hosted display, interface, and code typography.
- Flat content surfaces, soft overlay depth, and mobile sheets.

Qualitative authority is [PRODUCT.md](PRODUCT.md) and the [committed surface brief](apps/web/.impeccable/surfaces/apps-web-src-client-app-tsx.md). Values come from [index.css](apps/web/src/client/index.css), the shared [UI components](apps/web/src/client/components/ui), [layout components](apps/web/src/client/components/layout), and the reader, notes, and graph implementations cited below. This records the implemented visual system; it does not approve code, CI, or deployment.

Frontmatter is normative. Unsuffixed appearance-dependent color and component entries describe the default Dark appearance; their `-light` siblings describe the Light override. This flattening fits the portable token schema without inventing a second theme mechanism. At runtime, use the existing semantic CSS properties and `html[data-theme='light' | 'dark']`; do not select literal palette entries inside components. The sidecar extends these tokens with motion, depth, breakpoints, and framework-free component samples. No synthetic tonal ramps are introduced: the source defines role pairs, not an authored eight-step ramp.

## Colors

The palette pairs green-tinted ink and warm white with a restrained emerald interaction color; secondary hues describe content and state.

### Primary

- **Emerald interaction** (`accent-primary`, `accent-primary-light`): explicit primary actions, selected navigation icons, focus, caret, and native control accents.
- **Emerald wash** (`accent-primary-soft` and its Light sibling): selected navigation backgrounds, text selection, search highlights, and input focus halos. Preserve its authored alpha value in each appearance.
- The runtime emerald aliases resolve to the primary pair. The legacy button variant named `violet` also renders emerald; its name does not authorize a purple primary action.

### Secondary

- **Knowledge violet** (`accent-violet` and its soft pair): content links, note/editor syntax, and knowledge-related indicators. It has a semantic role rather than serving as a second general interaction accent.
- **Success, warning, and danger** (`app-success-fg`, `app-warning-fg`, `app-danger`, with Light siblings): state text and recovery actions. The runtime amber and rose aliases share warning and danger values. Shared status badges retain category tints around these semantic foregrounds; the destructive button retains its authored rose tint.

### Tertiary

- **Graph knowledge categories** (`graph-node-*`, with Light siblings): transcript, note, folder, entity, topic, claim, event, cluster, and content. Each hue identifies a node type in [graph-model.ts](apps/web/src/client/lib/graph-model.ts), shared by graph renderers. These colors are not additional UI themes.
- **Graph label ink and active violet** (`graph-label`, `graph-active-node`, with Light siblings): readable names and selected graph nodes. Relationship edges encode relation kinds; the overview uses preblended neutral edges to avoid opacity buildup. Keep those mappings in the graph palette rather than borrowing them for interface chrome.

### Neutral

- **Ink / warm-white ground** (`app-bg` pair): page and canvas foundations.
- **Raised ground** (`app-bg-elevated` pair): header, fields, overlay content, and the elevated card variant.
- **Document surface and hover layer** (`app-surface`, `app-surface-hover` pairs): contained data, contextual groups, and interaction feedback.
- **Thin rule / strong rule** (`app-border`, `app-border-strong` pairs): separators and container edges / field and secondary-control edges.
- **Reading ink / secondary ink / metadata ink** (`app-fg`, `app-subtle`, `app-muted` pairs): primary text / supporting text / secondary information and placeholders. Supporting and muted roles are not interchangeable.
- **Inverted control** (`app-inverted`, `app-inverted-fg`, `app-inverted-hover` pairs): the high-contrast default button.
- **Overlay scrim** (`app-scrim`): the shared backdrop behind protected-focus overlays in both appearances.

### Named Rules

**The One Identity Rule.** Change appearance through the semantic property overrides; keep the logo, type, hierarchy, and component vocabulary consistent across Light and Dark.

**The Semantic Color Rule.** Emerald identifies interaction; status, source, syntax, and graph colors retain their own meanings. Do not turn the knowledge palette into decorative interface accents.

## Typography

**Display Font:** Bricolage Grotesque, with Inter and sans-serif fallbacks.
**Body Font:** Inter, with the interface stack recorded in frontmatter.
**Label/Mono Font:** Inter for labels; JetBrains Mono for code, source identifiers, timestamps, and data.

All three faces are self-hosted under `/fonts/`, with swap loading. The shipped weight ranges are Inter (400–700), Bricolage Grotesque (500–700), and JetBrains Mono (400–500). The interface enables `cv11`, `ss01`, and `ss03`; its base tracking is neutral. The display voice is compact and expressive while reading remains calm and familiar.

### Hierarchy

- **Display** (`display`): the public authentication story at large widths, not the default application heading. Its fluid scale and tight line spacing are recorded in frontmatter.
- **Headline** (`headline`, `headline-sm`): shared page titles; switch at the small breakpoint. Descriptions use small interface text with relaxed leading and a constrained measure.
- **Document title** (`document-title`, `document-title-sm`, `document-title-lg`): reader headings; step at the small and large breakpoints. Balance lines, allow long words to wrap, and keep source identifiers constrained.
- **Title** (`title`): shared card/dialog titles. The imported Astryx heading layer uses the heading-family bridge, so these remain Bricolage even when the component only declares size and weight. Content section headings and note titles retain that display voice.
- **Body** (`body`): document Markdown and summaries. The reader constrains prose to a readable measure (75ch). The general Markdown renderer has a smaller default (14.5px with 1.625 leading); document views explicitly override it with the reading role. Timestamp transcript prose uses its own observed setting (15.5px with 1.85 leading).
- **Interface / label** (`interface`, `label`, `label-strong`): fields and controls; primary buttons strengthen the label weight. Descriptions use relaxed leading (1.625). Fields become large enough to avoid mobile input zoom (16px) on coarse pointers.
- **Small label / code** (`label-small`, `code`): badges and compact metadata / fenced code and source data. Tabular numerals support counts and timestamps. Compact metadata varies locally; it is not a replacement for body text or a global overline style.

### Named Rules

**The Reading Measure Rule.** Preserve the document's prose measure and heading hierarchy when adding tools, metadata, or wider tables; extra workspace width must not stretch the reading column.

## Layout

The shared [PageShell and PageHeader](apps/web/src/client/components/ui/page-shell.tsx) align titles, descriptions, actions, and body content. Shell widths come from [interface-foundation.ts](apps/web/src/client/lib/interface-foundation.ts): reading (72rem), workspace and wide (1600px). The spacing scale is based on a quarter rem; half steps support compact controls without introducing a second density system.

PageShell uses compact horizontal/vertical padding (1.25rem / 1.5rem), then increases both at the small breakpoint (2rem), with wider horizontal padding at the extra-large breakpoint (2.5rem). Section separation steps from the `7` spacing token to `8`. Headers stack actions beneath the title on small screens, then align them in a wrapping row. Widths are maximums, not minimums: child content must be able to shrink and wrap.

At the medium breakpoint, the application mounts the Astryx SideNav in a 264px rail and TopNav in a 4rem header. Raised chrome surrounds a page-ground content surface with a 1px rule, 16px corners, and 12px outer inset. Sidebar collapse moves the surface while returning focus to the available toggle, without remounting page content. On mobile, the approved bottom navigation and accessible contextual drawer remain in place. Four content destinations plus profile share the bottom bar (4rem high, plus bottom safe area). Main content reserves space for it; routes with their own chrome follow the shell's existing navigation policy.

Desktop Library hover and focus treatments extend 16px beyond the aligned content on each side, with 12px corners. The thumbnail, title, and metadata do not move. The separator remains aligned with the content rather than the expanded hover boundary.

The owner-approved replacement symbol is [voxen-symbol.png](apps/web/public/brand/voxen-symbol.png), a generated raster with actual alpha and no wordmark or enclosing background. Browser/navigation icons preserve transparency; installed maskable and Apple icons place it on the existing warm-white ground inside their safe area. Generation provenance is embedded in each PNG. The owl is no longer part of the product identity.

Phones use a portrait manifest preference and native orientation locking where available to installed apps. On coarse-pointer screens with a shorter physical dimension below 600 CSS pixels, landscape displays a modal instruction; page state and input remain mounted. Physical orientation detection avoids confusing software-keyboard viewport changes with rotation. Desktop and tablet browsers remain usable in landscape.

Use the existing small, medium, large, and extra-large viewport breakpoints from the sidecar. Responsive behavior also follows available component width: local graphs change at a container width (680px), global graph inspectors at (720px), and the note toolbar at its container threshold (42rem). Reader tools move beside prose only when the extra-large layout has space (280px tool column). The notes list similarly gains an adjacent tree (220px) at that breakpoint. Public authentication uses a single form column on small screens and reveals its story beside the form at the large breakpoint.

Dialogs become bottom sheets below the medium breakpoint. Keep their full-width mobile footprint, internal scrolling, viewport-height ceiling, safe-area padding, and keyboard offset. Use `--visual-viewport-height` and `--visual-viewport-bottom` rather than assuming a fixed screen height; the bottom navigation hides while the mobile keyboard is open. Do not use horizontal clipping as a substitute for preserving readable content and reachable controls. Tables and code may scroll within their own region.

Touch affordances follow pointer capability as well as width. Coarse-pointer buttons, selects, and ordinary inputs receive a minimum hit region (44px on each axis). Checkbox/radio and Switch visuals are excluded from that generic enlargement. Explicit close controls are touch-sized. The Switch keeps its small painted track and expands its hit region separately; its geometry is specified under Components.

## Elevation & Depth

Content is flat at rest. Thin rules and tonal differences separate lists, cards, editor regions, and chrome. The utility surface uses a rule and rounded corners; the elevated card changes its ground without adding a shadow. Hoverable cards strengthen the border without lifting or translating. The source's old card comment does not define hover behavior.

### Shadow Vocabulary

- **Overlay** (`overlay` in the sidecar): the shared soft, offset shadow for dialogs and sheets, paired with the scrim.
- **Overlay medium / large / extra-large** (`overlay-md`, `overlay-lg`, `overlay-xl` in the sidecar): existing graph-feedback, select/appearance-popover, and menu/default-popover depth from the imported utility scale. Tooltips use a ruled raised ground without a shadow. These are floating context, not the resting treatment for document rows or cards.

### Named Rules

**The Flat Content Rule.** Use rules and tonal layering for persistent content; reserve soft shadow depth for floating or temporary context.

Motion supports state and orientation: short color changes for controls, a small press response for buttons, an optional already-visible page reveal, and short navigation transitions. The sidecar records the actual easing and durations. PageShell revelation is opt-in and respects reduced motion; it must not hide content while waiting for animation. Under reduced motion, remove decorative entrances, page reveal, press transforms, and collapsible/text-shimmer motion through the existing reduced-motion paths. View transitions shorten to their minimum duration. Legacy ungated effects are drift, not permission to add perpetual motion.

## Shapes

The form language is gently curved and ruled. The authored radius scale is preserved in frontmatter: small details, fields, buttons, and contained surfaces use their existing steps. Shared buttons use `lg`, fields use `md`, and the legacy Card uses the imported `2xl` step. DataSurface and utility surface classes use their own authored `xl` / `lg` choices; do not infer that every container has the same radius from a brief.

Mobile overlays round their top corners using the `2xl` step. Desktop dialogs round all corners using `xl`; desktop side sheets meet the viewport edge with square corners. Badges and the Switch use full rounding. Disclosure rows remain square, with an inset focus ring so focus is visible inside clipped collection boundaries. Most separators and control edges use a thin stroke (1px); heading and reading hierarchy carry the structure rather than ornamental framing.

## Components

### Buttons

Restrained, legible controls with explicit action hierarchy. [Button](apps/web/src/client/components/ui/button.tsx) wraps Astryx for accessible control behavior and applies Voxen's appearance tokens. Keep the wrapper as the implementation entry point.

- **Shape and size:** standard labels use `label`, the `lg` radius, and the frontmatter padding. Default and large sizes have a minimum height (2.5rem); small uses (2.25rem), extra-large (3rem), and icon-only uses a square (2.5rem). Coarse-pointer sizing preserves the touch minimum. Large and extra-large sizes use wider horizontal padding (1.25rem / 1.75rem); extra-large uses `xl` rounding and base-sized text.
- **Default / primary:** inverted high contrast / emerald with the page-ground foreground. Default hover uses the inverted-hover token; primary hover brightens its existing fill (1.1). The `violet` API variant is an alias of primary.
- **Secondary / outline:** surface-filled or transparent, with a strong rule. Hover uses the next authored surface layer.
- **Ghost / disclosure:** quiet foreground and transparent ground, gaining a surface on hover. Disclosure is square, retains its scale on press, and uses an inset focus ring.
- **Destructive / link:** danger foreground with the authored rose category tint / foreground text that underlines and changes to the interaction color on hover.
- **States:** visible focus uses the theme focus color with a ring (2px) and page-ground offset (2px), except disclosure. Press scale (0.98), short transitions, disabled opacity (0.5), and reduced-motion overrides come from the shared component. Icon-only controls require accessible labels.

The sidecar has a separate sample for every public button variant, including the compatibility alias. Its samples flatten the wrapper's appearance into native HTML/CSS; the application continues to use Astryx.

### Chips

Default, outline, and muted variants use semantic grounds, rules, and text. Success/warning/danger variants add category tints around the corresponding semantic foregrounds. Badges are static annotations; a badge-shaped filter must remain an actual control with the existing focus and hit-target treatment. Source and graph categories retain their meaning rather than inheriting the interaction accent indiscriminately.

### Cards / Containers

The elevated variant changes to the raised ground. Shared headers, content, and footers use the `6` spacing token; content and footer omit the top inset. Card titles use `title`. The hoverable option only strengthens the rule.

Documentary library entries are continuous content rows with bottom rules and quiet metadata, not a requirement to wrap every record in a Card. ### Inputs / Fields

Clear boundaries with a quiet raised ground. [Input](apps/web/src/client/components/ui/input.tsx) uses the strong border, `md` radius, full width, and the recorded field geometry. ### Dialogs and Sheets

Protected temporary context. [Dialog](apps/web/src/client/components/ui/dialog.tsx) and [Sheet](apps/web/src/client/components/ui/sheet.tsx) share the scrim, raised ground, overlay shadow, and accessible focus/dismissal primitives. Dialogs use a mobile bottom-sheet footprint and become centered at the medium breakpoint, with the standard maximum width (32rem) and viewport-side clearance (3rem total). Sheets become edge-aligned side panels at that breakpoint (32rem wide).

Both cap mobile height against the current visual viewport (90dvh ceiling). Dialog padding uses the `5` horizontal and `7` top spacing tokens, a safe bottom inset, and then uniform `7` padding on desktop. Sheet content owns its internal padding. Close buttons have a square hit region (44px); dialog title/description reserve room for them. Footer actions stack in reverse order on mobile and align to the end on desktop. Preserve scrolling, safe areas, focus containment, and back-to-dismiss behavior together.

### Switch

A small painted control with a separate touch region. [Switch](apps/web/src/client/components/ui/switch.tsx) has a track (44px wide, 24px high), a thumb (20px square), and full rounding. The strong rule colors its unchecked track and border; checked state uses emerald. The thumb uses the raised ground and translates between its authored offsets (2px / 20px).

The transparent pseudo-element extends the track vertically (10px above and below), creating a hit region (44px square). Do not enlarge the painted track to meet the generic coarse-pointer minimum. Preserve the switch role, checked/disabled state, visible focus, and enough surrounding space for that hit region. Track color changes use a short transition; the thumb uses the shared ease-out timing.

## Do's and Don'ts

### Do:

- **Do** use the existing semantic properties for both appearances and preserve the approved transparent Voxen symbol.
- **Do** align page titles, actions, and content through the shared shell and spacing scale.
- **Do** keep document prose constrained, headings semantic, and metadata quieter than content.
- **Do** preserve mobile sheets, safe areas, keyboard offsets, visible focus, selection color, and touch hit regions together.
- **Do** keep graph, status, source, and syntax colors tied to their existing meanings.
- **Do** honor reduced motion and leave content visible when optional animation cannot run.

### Don't:

- **Don't** introduce another appearance pack, decorative accent palette, the retired owl, or unapproved replacement branding.
- **Don't** turn every content row into a card, add nested decorative containers, or shadow persistent content.
- **Don't** shrink desktop dialogs onto mobile or rely on gestures as the only way to navigate or dismiss context.
- **Don't** enlarge the Switch's painted track to satisfy its separate touch hit region.
- **Don't** use monospace as decoration, add invented illustrations, or add kickers above headings.
- **Don't** promote local hard-coded focus colors, appearance-specific text overrides, or ungated decorative motion into shared rules.
